# 面试追问手册

## 用 60 秒介绍项目

FlashFlow 是一个高并发限量购与订单履约平台。我把它拆成网关、交易和通知三个服务。请求先经过 Gateway 的 JWT 校验和 Redis 限流，交易服务用 Lua 原子完成库存预占、用户限购和请求幂等，再通过 MySQL 条件更新做最终防超卖。订单和 Outbox 事件在同一事务提交，调度器把事件至少一次投递到 Kafka，通知服务用 Inbox 表按 `eventId` 去重，失败消息重试后进入 DLT。Redis 补偿失败会落成可重试的任务，残留漂移由带静默窗口和 CAS 的对账任务修复。正确性用 Testcontainers 在真实 MySQL/Redis/Kafka 上做并发和故障注入测试，性能用 2 万个独立买家的 k6 压测验证。

## 为什么不用 Redis 分布式锁扣库存

锁会把热点请求串行化，还要处理租约、续期、锁误释放。库存扣减本身是一个很短的原子状态转换，Lua 更适合一次完成检查与写入。项目中的分布式锁只用于低频的 Outbox 调度协调，业务正确性不依赖这把锁。

## Redis 已扣、MySQL 失败怎么办

交易服务捕获数据库事务失败，立即执行带订单号校验的 Lua 补偿。补偿脚本只有在幂等映射仍属于当前订单号时才恢复库存，所以重复执行是安全的。如果这次即时补偿也失败（Redis 抖动），就用 `REQUIRES_NEW` 新事务写一条 `stock_compensation_task`，由重试任务按指数退避继续执行；如果连 MySQL 也写不进去，再由定时对账兜底。

## 取消、超时、退款后的 Redis 回补怎么保证不丢

这三种情况 MySQL 库存已经在事务中回补，Redis 必须跟上，否则活动会提前“售罄”。做法和 Outbox 一样：在回补库存的同一事务里插入补偿任务，提交后立即执行一次，失败则留给重试任务，耗尽 12 次进入 `FAILED` 并触发 critical 告警，运营可在后台修复后手动重试。故障注入测试用 `docker pause` 冻结 Redis 验证过：恢复后库存恰好回补一次。

## 客户端超时了，Redis 到底执行没有

不知道，也不需要知道。Lettuce 超时只是客户端放弃等待，命令可能已经在 Redis 排队，恢复后照常执行——集成测试里确实观察到了这种情况。正确做法是让操作幂等：补偿脚本按订单号判断，第二次执行返回 0（`NOOP`），所以“超时后重试”永远安全。

## 对账会不会把正常的在途预占当成漂移

会，如果一看到差异就修。在途预占（Redis 已扣、MySQL 未提交）本来就会让 Redis 暂时小于 MySQL。对账只在两次观察之间活动行版本号和 Redis 值都没变、且持续超过静默窗口（默认 30 秒）时才修复；修复用 Lua CAS，只有 Redis 仍等于观察值才写入；该活动还有待执行补偿任务时直接跳过。即使误修，Redis 也只会偏大，MySQL 条件扣减仍然防超卖。

## 为什么不能只用单用户压测

早期压测用一个账号放宽限流后打到 800 次/秒，但这个场景让地址快照缓存始终命中，掩盖了每单一次只读 JPA 事务（约 7 次 MySQL 往返）的成本。换成 2 万个独立买家、默认限流配置后，真实容量只有约 250 单/秒。用 JFR 定位到慢的是 MySQL 往返而不是 CPU，随后把地址读取改成单条自动提交 SQL、去掉 Outbox 的 merge SELECT、把订单主键改成可批量插入的号段，容量回到约 670 单/秒。教训是压测数据分布要和真实流量一致。

## 为什么 MySQL 还要条件扣减

Redis 可能因为数据初始化错误、人工误操作或故障恢复而与数据库不一致。条件更新是最终防线，影响行数不为 1 就回滚订单事务并补偿 Redis。两层控制分别解决吞吐和最终正确性。

## Outbox 能保证 Exactly Once 吗

不能宣称端到端 Exactly Once。Outbox 保证数据库提交后的事件最终可发送，但“Kafka 已收到、Outbox 尚未标记”时进程崩溃会产生重复消息。因此整体使用 At-Least-Once + Consumer Inbox Idempotency，实现一次业务效果。这个表述比笼统说“Kafka Exactly Once”更准确。

## 为什么 Producer 还开幂等

Kafka Producer 幂等能消除同一 Producer 会话内因网络重试导致的重复记录，并配合 `acks=all` 提高可靠性；它不能替代跨进程、跨事务的 Outbox，也不能替代消费者业务幂等。

## 如何保证同一订单事件有序

所有订单事件都用 `orderNo` 作为 Kafka key，因此同一订单进入同一分区。Kafka 只保证分区内顺序，不保证整个 Topic 全局有序。消费者还应校验状态机，防止非法状态迁移。

## 幂等键应该由谁生成

客户端为一次业务意图生成随机且稳定的 `Idempotency-Key`，超时重试沿用原值；新业务意图必须生成新值。服务端把它与用户 ID 组合，避免不同用户之间碰撞。

## 网关限流和业务限流为什么都要有

网关限流保护整个系统和网络入口，粒度较粗；交易服务限流靠近业务资源，可按用户和具体活动控制。只做网关限流无法表达“一个用户每秒最多发起 5 次秒杀”这类规则。

## 订单超时取消与支付并发怎么办

支付和取消都在订单实体状态机上执行，并受 JPA `@Version` 乐观锁保护。只有 `PENDING_PAYMENT` 能转移到 `PAID` 或 `CANCELLED`；并发事务中一个成功，另一个会因版本或状态不匹配失败。真实支付回调还需要渠道流水号唯一约束。

## Redis 库存为何设置 TTL

TTL 覆盖活动结束时间并额外保留一天，避免活动 key 永久堆积，也给超时关单和排障留出窗口。即使 key 提前丢失，系统选择停止售卖，而不是绕过 Redis 造成压力或风险。

## 项目如何继续增强

优先级从高到低：

已完成：Testcontainers 全链路集成测试（含故障注入）、库存补偿任务与对账、Prometheus 告警规则、Outbox 保留期清理。后续优先级：

1. Debezium CDC 替换轮询 Outbox；
2. OpenTelemetry 跨 HTTP/Kafka 链路追踪；
3. DLT 管理后台与一键重放；
4. 单活动写入仍是单线程，继续提升需要库存分桶（多个写分片各持一部分库存）；
5. Kubernetes、HPA、PodDisruptionBudget 和多可用区中间件；
6. 支付回调签名、退款与渠道流水幂等；
7. 在独立压测机上做 30 分钟以上稳态测试，避免压测器与被测服务抢 CPU。

## 面试时不要这样说

- 不要说“绝对不超卖”，要说明假设、最终防线和故障模型；
- 不要把 Redis 锁等同于分布式事务；
- 不要把 Kafka Producer 幂等说成端到端 Exactly Once；
- 不要声称没有亲自测过的 QPS、P99 或数据量；
- 不要只背组件名，要能从代码指到 Lua、索引、唯一约束、Outbox 和 Inbox。
