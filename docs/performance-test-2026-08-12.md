# FlashFlow 本地性能测试报告

测试日期：2026-08-12

## 1. 测试目标

本次测试不只关注请求吞吐，还核对以下工程目标：

- 持续成功下单时的稳定吞吐与响应延迟；
- 超过系统处理能力后出现的性能拐点和真实瓶颈；
- 热点活动售罄后的快速拒绝能力与库存正确性；
- 同一请求重复提交时的订单幂等性；
- 默认网关和交易服务限流是否生效；
- 数据库库存、Redis库存、成功订单数是否一致；
- Outbox事件能否最终全部投递并被通知服务幂等消费。

## 2. 测试环境

| 项目 | 配置 |
| --- | --- |
| 操作系统 | Windows 11 专业工作站版 |
| CPU | AMD Ryzen 9 8940HX，16核32线程 |
| 物理内存 | 31.2 GB |
| Docker可用内存上限 | 约15.2 GB |
| 部署方式 | Docker Compose，本机单实例部署 |
| 服务 | Gateway、Trade、Notification各1实例 |
| 中间件 | 单节点MySQL、Redis、Kafka |
| 压测工具 | k6 0.57.0 Docker镜像 |
| 交易服务数据库连接池 | 20个连接，获取连接超时3秒 |

压测器与被测服务运行在同一台电脑，因此结果只代表这台本地机器及当前容器配置，不能直接等同于生产环境容量。

由于演示环境只有一个用户账号，核心容量测试使用 `compose.benchmark.yml` 临时提高了按用户限流阈值，以避免测试结果被单用户保护策略截断。完成测试后已恢复项目默认限流配置，并单独验证了默认保护策略。

## 3. 测试方法

1. 创建独立压测商品和高库存SKU，每档测试使用独立秒杀活动隔离数据；
2. 先以20请求/秒预热10秒，使JIT、连接池和缓存进入工作状态；
3. 分别以50、100、120、150、200和400请求/秒发送唯一幂等请求；
4. 每档持续20秒，记录成功数、服务端错误、掉队请求、平均响应时间和P95；
5. 另建200件库存活动，以500请求/秒验证热点库存保护；
6. 使用100个并发用户重复提交同一幂等键1000次；
7. 测试后核对MySQL订单、MySQL库存、Redis库存、Outbox和通知消费数量。

## 4. 持续下单测试结果

| 目标请求速率 | 实际完成速率 | 成功订单 | 服务端错误 | 掉队请求 | 平均响应 | P95 | 结论 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 20/s（预热） | 20.04/s | 201 | 0 | 0 | 35 ms | 49 ms | 正常 |
| 50/s | 50.00/s | 1,001 | 0 | 0 | 24 ms | 32 ms | 稳定 |
| 100/s | 99.94/s | 2,001 | 0 | 0 | 24 ms | 41 ms | 稳定 |
| 120/s | 119.93/s | 2,401 | 0 | 0 | 20 ms | 50 ms | 稳定工作点 |
| 150/s | 141.89/s | 3,001 | 0 | 0 | 692 ms | 1,134 ms | 开始明显排队 |
| 200/s | 132.76/s | 3,159 | 101 | 741 | 3,531 ms | 5,224 ms | 超过容量 |
| 400/s | 197.56/s | 3,147 | 1,681 | 3,173 | 4,709 ms | 5,983 ms | 严重过载 |

说明：k6的“实际完成速率”按测试总耗时计算，其中包括测试结束后的在途请求完成时间；因此150/s档虽然没有掉队，但完成速率为141.89/s且延迟已显著升高。

### 容量判断

- 当前单实例、默认20个数据库连接的配置下，约120笔成功下单/秒是较稳妥的本地工作点；
- 150请求/秒仍可全部完成，但P95超过1秒，已经不适合作为稳定容量；
- 200请求/秒及以上时，成功处理能力约停留在129笔/秒附近，同时开始产生连接获取超时和请求掉队；
- 因此不能把“400并发下单”或峰值请求数当作稳定吞吐。

## 5. 性能瓶颈

200和400请求/秒档位的服务日志显示：

- 交易服务数据库连接池20个连接全部占用；
- 等待连接的请求一度超过280个；
- 请求等待3秒后发生数据库连接获取超时，最终返回5xx；
- Redis库存脚本没有出现执行错误，失败请求的预扣库存随后被补偿。

当前首要同步链路瓶颈是数据库连接池及热点活动库存行的竞争，而不是Redis。单纯增大连接池不一定能线性提高性能，还需要减少下单事务中的查询次数、优化热点行更新方式，并设置更明确的过载保护。

异步链路也存在独立瓶颈：Outbox每次最多读取50条，并在固定周期内逐条等待Kafka确认。因此当订单创建速度长期高于约50条/秒时会产生事件积压。测试中曾观察到6,537条待投递事件；停止压测后积压自动下降，最终全部完成投递和消费。

| --- | ---: |
| 总请求数 | 1,001 |

## 9. 一致性核对

正式测试活动均满足：

```text
活动初始库存 = 未发生库存补偿的有效订单购买数量 + 最终剩余库存
MySQL最终库存 = Redis最终库存
```

特别是在200和400请求/秒档位出现数据库连接超时后，Redis与MySQL库存仍完全一致，说明失败请求的库存补偿生效。

在主要性能档位完成并等待异步积压清空的固定检查点：

| 项目 | 数量 |
| --- | ---: |
| Outbox已发布事件 | 15,177 |
| Outbox待发布事件 | 0 |
| 通知服务已处理事件 | 15,177 |
| 生成站内通知 | 15,177 |

数量完全一致，未出现消息丢失或重复通知。

后续资源采样和测试订单超时自动取消会继续生成新的事件，因此这里记录固定检查点，不把持续变化的事件总量当作吞吐指标。

Docker的CPU百分比按逻辑核心累计，超过100%表示使用了多个核心。该次重复测试在数据量增长且异步任务并行运行时P95为352 ms，明显高于前一轮120请求/秒的50 ms，说明短时本机结果存在运行阶段差异。若用于正式容量规划，应迁移到独立压测机，使用固定数据集并延长稳态测试时间。

## 11. 后续优化建议

按优先级建议：

1. 为数据库连接池、请求队列和业务入口设置协调的容量上限，过载时尽早返回，避免请求等待数秒后才失败；
2. 对单活动热点库存行进一步评估库存分桶、请求合并或队列串行化方案；
3. 增加库存补偿失败后的重试与自动对账任务，形成可自动恢复的闭环；
4. 为活动缓存命中率、连接池等待、Outbox 待发布量、Kafka Lag 和订单失败率设置告警；
5. 在 CI 或独立测试环境中加入 30 分钟以上的稳态压测、峰值测试和故障注入测试。

## 12. 第一轮性能优化实施与复测

根据首轮测试定位的同步事务和异步链路瓶颈，本轮完成了以下优化：

1. 将活动状态、价格、限购等稳定数据改为短时本地快照，并对并发缓存未命中使用单飞加载，避免大量请求重复读取同一活动、商品和 SKU；
2. 将商品快照读取移出下单事务，缩短数据库连接和热点库存行的占用时间，同时保留统一的库存更新顺序以避免外键锁升级死锁；
3. 开启 JDBC 预编译语句缓存并预热连接池，减少高频 SQL 的重复解析和突发建连开销；
4. 将 Outbox 从“每秒最多 50 条、逐条等待确认”调整为“每 100 毫秒最多 500 条、并发发送、批量更新发布状态”，并启用 Kafka Producer 批处理和 LZ4 压缩；
5. 通知服务改为 Kafka 批量拉取、批量事务写入和 3 个消费者并发处理，避免 Outbox 提速后通知服务反向争抢同一个 MySQL 实例。

复测仍使用相同机器、相同 Docker 单实例拓扑、相同 20 个交易数据库连接和相同的 20 秒测试时长：

| 档位 | 版本 | 成功订单 | 成功完成速率 | 服务端错误 | 丢弃请求 | 平均响应 | P95 |
| ---: | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 120/s | 优化前 | 2,401 | 119.93/s | 0 | 0 | 20 ms | 50 ms |
| 120/s | 优化后 | 2,401 | 119.96/s | 0 | 0 | 20.87 ms | 70.20 ms |
| 150/s | 优化前 | 3,001 | 141.89/s | 0 | 0 | 691.78 ms | 1,133.68 ms |
| 150/s | 优化后 | 3,001 | 149.66/s | 0 | 0 | 21.97 ms | 70.46 ms |
| 200/s | 优化前 | 3,159 | 128.65/s | 101 | 741 | 3,531 ms | 5,223.78 ms |
| 200/s | 优化后 | 3,534 | 152.80/s | 67 | 400 | 2,432.08 ms | 3,334.78 ms |

在关键的 150/s 档位，优化后仍完成全部 3,001 笔订单且没有 5xx 或丢弃请求，P95 从 1,133.68 ms 降至 70.46 ms，下降约 93.8%；本机可稳定工作点由 120/s 提升到 150/s，提升 25%。120/s 档位的 P95 有小幅波动，说明本地同机压测结果受 JVM、Docker 和后台任务运行阶段影响，不能宣称所有低负载延迟都同步下降。

200/s 档位的成功吞吐和错误数均有改善，但仍出现 67 个 5xx 和 400 个调度器丢弃请求，因此 200/s 只能视为过载档，不能写成稳定处理能力。当前剩余瓶颈仍是单活动 MySQL 库存行串行更新、单交易实例和压测器与服务共享宿主机资源。

优化后的正确性回归结果：

| 场景 | 结果 |
| --- | --- |
| 500 请求/秒、200 件库存售罄 | 5,001 个请求中恰好 200 个成功、4,801 个业务拒绝、0 个 5xx；MySQL 与 Redis 最终库存均为 0 |
| 同一幂等键并发重放 1,000 次 | 100% 返回同一订单，仅写入 1 笔订单，仅扣减 1 件库存，P95 为 72.86 ms |
| 消息最终一致性检查点 | Outbox 已发布 57,278 条、通知 57,278 条、Inbox 处理 57,278 条，待发布为 0，Kafka Lag 为 0 |

复测说明本轮优化没有破坏防超卖、请求幂等和消息消费幂等。测试期间还通过压力回归发现并修复了虚拟线程执行阻塞式缓存加载时的载体线程占用问题，并用自动化测试固定了数据库写入顺序，防止以后重构重新引入锁顺序问题。

## 13. 第二轮热点事务合并优化与复测

第一轮优化后，MySQL 语句统计显示单活动库存行更新累计平均耗时约 104.20 ms，而订单插入平均约 0.37 ms，说明继续压缩普通查询和对象创建已经不是首要矛盾，主要问题是大量独立事务同时等待同一库存行。

第二轮引入按活动路由的有界单写队列与微批量事务：

1. 根据活动 ID 将写请求路由到固定写入分片，同一活动只由一个工作线程顺序提交，避免大量事务在数据库连接池中等待同一行锁；
2. 在 8 ms 窗口内最多合并 64 个同活动订单，把多次库存扣减合并为一次按总购买数量的 MySQL 原子扣减；
3. 批次内订单与对应 Outbox 事件仍在同一个本地事务中提交，并使用 Hibernate JDBC Batch 批量写入 Outbox；
4. 每个分片设置 2,048 个请求的有界队列，队列满时返回受控 429，由原有补偿逻辑恢复 Redis 预占，避免数据库连接耗尽后产生 5xx；
5. 增加批次大小、拒绝次数和队列相关指标，并补充同活动并发合并、合并扣库存和关闭阶段处理测试。

| 目标速率 | 成功订单 | 成功完成速率 | 业务拒绝/429 | 5xx | 丢弃请求 | 平均响应 | P95 | 结论 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 150/s | 3,000 | 149.82/s | 0 | 0 | 0 | 32.68 ms | 62.41 ms | 稳定 |
| 200/s | 4,001 | 199.80/s | 0 | 0 | 0 | 25.14 ms | 35.14 ms | 稳定 |
| 250/s | 5,000 | 249.87/s | 0 | 0 | 0 | 24.94 ms | 35.35 ms | 稳定 |
| 300/s | 6,001 | 299.63/s | 0 | 0 | 0 | 24.97 ms | 34.47 ms | 稳定 |
| 400/s | 8,001 | 399.40/s | 0 | 0 | 0 | 35.17 ms | 62.67 ms | 稳定 |
| 500/s | 10,000 | 499.00/s | 0 | 0 | 0 | 33.75 ms | 50.72 ms | 稳定 |
| 750/s | 15,000 | 748.64/s | 0 | 0 | 0 | 69.32 ms | 153.56 ms | 稳定 |
| 800/s | 16,001 | 797.64/s | 0 | 0 | 0 | 96.08 ms | 149.16 ms | 本轮最高稳定档 |

第二轮使 200/s 档位从 67 个 5xx、400 个丢弃请求和 3,334.78 ms P95，改善为 4,001 个请求全部成功、零错误、零丢弃和 35.14 ms P95。以相同的 20 秒短时测试口径计算，本机已验证稳定工作点从第一轮的 150/s 提升至 800/s，约为原来的 5.3 倍。

在本轮固定检查点，85,194 笔成功下单合并为 7,306 次库存事务，平均每次事务处理约 11.66 笔订单，热点库存更新次数减少约 91.4%。Outbox 已发布、通知和 Inbox 处理数量均为 144,172，待发布事件为 0，Kafka Lag 为 0，说明吞吐提升没有把积压转移给异步链路。

正确性回归中，500 请求/秒冲击 200 件库存时恰好成功 200 单、4,801 次业务拒绝、0 个 5xx，MySQL 与 Redis 库存均为 0；同一幂等键并发重放 1,000 次仍只生成 1 笔订单、只扣减 1 件库存，P95 为 58.88 ms。

1,000/s 档位没有出现 5xx，但已经产生 429、请求丢弃和秒级排队，因此只能证明过载保护有效，不能作为稳定容量。该档位最终生成 17,888 个唯一订单，MySQL 与 Redis 剩余库存均为 2,612，证明队列拒绝后的预占补偿有效。800/s 也只是本机共享宿主机、单实例、20 秒短测的结果，正式容量规划仍需要独立压测机和更长时间的稳态测试。
