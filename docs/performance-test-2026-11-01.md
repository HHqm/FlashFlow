# FlashFlow 性能与正确性测试报告（多买家）

测试日期：2026-11-01

上一版报告（[2026-08-12](performance-test-2026-08-12.md)）用一个演示账号并放宽限流做压测。本轮改为 2 万个独立买家、全部默认限流配置，结果暴露了单用户压测掩盖的真实瓶颈。本报告记录测试方法、瓶颈定位过程、优化前后对比和最终结果。

## 1. 环境

| 项目 | 配置 |
| --- | --- |
| 机器 | AMD Ryzen 9 8940HX（16 核 32 线程），31.2 GB 内存，Windows 11 |
| Docker | Docker Desktop，32 vCPU / 15.2 GB 内存可用 |
| 部署 | `docker compose up -d`，Gateway、Trade、Notification 各 1 实例；MySQL 8.4、Redis 8.4、Kafka 4.3 各 1 节点 |
| 关键参数 | 交易库连接池 20；单写队列 4 分片、8 ms 窗口、每批最多 64 单；InnoDB 缓冲池 512 MB |
| 限流 | 全部默认：网关每用户 50 次/秒（突发 100），交易服务每用户 5 次/秒 |
| 压测器 | k6 0.57.0，与被测服务同机，在 compose 网络内直接访问 `gateway-service:8080` |
| 数据 | 库内已有约 16 万历史订单；每档使用新建活动隔离 |

压测器与服务共享同一台机器，结果只代表本机单实例，不等同于生产容量。

## 2. 方法

`bash load-test/run-suite.sh` 一键执行：

1. 用 SQL 生成 2 万个无法登录的压测买家和默认地址，按 `AuthService` 相同的声明签发 JWT；
2. 每个场景新建活动，k6 用 `constant-arrival-rate` 定速发请求，**每个请求来自不同买家**；
3. 场景结束后等待 Outbox 积压清零，再核对：MySQL 剩余库存、Redis 库存、订单数、成交买家数、每个买家最多几单，判定是否超卖（`成交数量 = 总库存 − 剩余库存` 且剩余 ≥ 0）。

## 3. 最终结果

| 场景 | 目标速率 | 请求数 | 实际速率 | 成功 | 售罄 | 超限购 | 429 | 5xx | 成功 P50 | 成功 P95 | 成功 P99 | 超卖 | MySQL 余量 | Redis 余量 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- | ---: | ---: |
| 持续下单 | 500/s | 10,000 | 499.5/s | 10,000 | 0 | 0 | 0 | 0 | 19.5 ms | 29.6 ms | 170.7 ms | 否 | 2,500 | 2,500 |
| 持续下单 | 800/s | 16,000 | 799.2/s | 16,000 | 0 | 0 | 0 | 0 | 20.8 ms | 33.1 ms | 48.4 ms | 否 | 4,000 | 4,000 |
| 持续下单 | 1,000/s | 20,001 | 999.2/s | 20,000 | 0 | 1 | 0 | 0 | 22.8 ms | 37.3 ms | 52.0 ms | 否 | 5,000 | 5,000 |
| 热点抢购 | 2,000/s | 20,002 | 1,999.2/s | 1,000 | 18,000 | 1,002 | 0 | 0 | 91.8 ms | 124.7 ms | 139.4 ms | 否 | 0 | 0 |
| 单用户狂刷 | 100/s | 1,001 | 100.1/s | 55 | 0 | 0 | 946 | 0 | 20.0 ms | 24.7 ms | 26.7 ms | 否 | 1,945 | 1,945 |

说明：

- **持续下单**每档 20 秒，所有请求均成功、零 5xx、零掉队，每个买家最多 1 单，MySQL 与 Redis 余量一致。1,000/s 档有 1 个请求落到已购买家（买家池循环），被限购正确拒绝。
- 同一轮中 300/s 档是预热后的第一档，P95 为 1,080 ms 并有 89 个掉队请求；此前交易服务刚被上一次混沌测试重启，属于冷启动阶段，后续更高档位均稳定。正式引用时以 500/s 及以上为准。
- **热点抢购**：1 万个买家各抢 2 次，共 2 万次请求争抢 1,000 件库存。恰好 1,000 单成交且来自 1,000 个不同买家，其余 18,000 次售罄、1,002 次超限购被拒，拒绝请求 P95 仅 9.5 ms，MySQL 与 Redis 最终库存均为 0。
- **单用户狂刷**：一个买家以 100 次/秒持续 10 秒，只成交 55 单（约 5 单/秒，与交易服务默认单用户阈值一致），其余 946 次 429，没有占满下单资源。
- **幂等**：同一幂等键在 100 个并发执行单元下提交 1,001 次，数据库只生成 1 笔订单、只扣 1 件库存。由于使用默认限流，绝大多数重放在进入业务逻辑前被 429 拦截；“重放返回同一订单”由集成测试（并发 40 次）覆盖。

## 4. 混沌测试：压测中强杀交易服务

500 次/秒、40 秒的下单过程中，第 12 秒对交易服务执行 `docker kill -s KILL`，3 秒后重新启动。

| 指标 | 结果 |
| --- | ---: |
| 重启到健康检查通过 | 17 秒 |
| 停机期间失败请求（网关 5xx） | 6,781 |
| 客户端看到的成功 | 12,355 |
| 数据库实际订单 | 12,363 |
| 超卖 | 否（MySQL 余量 17,637） |
| 流量结束时 Redis 与 MySQL 差异 | −2（2 件预占随进程一起丢失） |
| 自动修复 | 流量停止 31 秒后由定时对账修复，审计日志记录 `17,635 → 17,637` |

- 8 笔订单已提交但响应随进程丢失，客户端会用同一幂等键重试并拿到原订单；
- 2 件被 `SIGKILL` 截断的预占没有补偿机会，正是对账任务要兜底的场景：静默窗口确认无在途写入后，用 Lua CAS 把 Redis 修回 MySQL 值；
- 全程没有超卖，修复后 MySQL 与 Redis 一致。

## 5. 瓶颈定位与优化过程

### 5.1 现象

首次多买家压测时，同一套代码在 200 次/秒就出现约 1 秒延迟，而 8 月单用户压测可到 800 次/秒。服务端指标显示下单接口平均 1.7 秒，单写队列平均每批 55 单（正常应为个位数），说明写线程被拖慢、请求在队列中排队。

### 5.2 定位

1. `performance_schema` 显示 MySQL 服务端执行很快（插入订单约 1.3 ms、提交约 3.4 ms），但 `SET autocommit`、`SET SESSION TRANSACTION READ ONLY`、`SELECT @@transaction_read_only` 的次数与订单数成倍数关系；
2. 用 JFR（`-XX:StartFlightRecording`）采样压测期间的交易服务：CPU 采样很少，时间主要花在等待；`jdk.SocketRead` 中慢于 10 ms 的 MySQL 读取有 892 次，近 60% 来自 `ShippingAddressService.resolveSnapshot`；
3. 根因：地址快照按（用户，地址）缓存，单用户压测时永远命中，掩盖了每单一次只读 JPA 事务（约 7 次 MySQL 往返）的成本；同时缓存没有上限，会随买家数无限增长。写线程内还有两个固定开销：Outbox 事件主键由应用生成，Spring Data 每条都先 `merge` 查一次；订单表 `IDENTITY` 主键使 Hibernate 无法批量插入，一批 55 单就是 55 次往返。

### 5.3 优化

| 步骤 | 改动 |
| --- | --- |
| A | 地址快照改为单条自动提交 SQL 并去掉无界缓存；`OutboxEntity` 实现 `Persistable`，新事件直接 `persist`；事件 ID 改为时间有序的 UUIDv7，Outbox/Inbox 主键顺序追加；Connector/J 开启 `useLocalSessionState` 等会话状态缓存 |
| B | InnoDB 缓冲池 128 MB → 512 MB；新增 Outbox 保留期清理（已投递事件保留 7 天、分块删除），表从 18 万行降到 6 万行 |
| C | 订单主键改为号段表生成器（每次取 500 个），配合 `rewriteBatchedStatements`，一批订单合并为一条多行 INSERT |

### 5.4 同口径对比

下表各步骤使用同一台机器、同一份数据、相同 20 秒档位，压测器统一经 Docker Desktop 的宿主机端口访问网关（与第 3 节的口径不同，只用于横向对比）：

| 目标速率 | 指标 | 优化前 | A | B | C |
| ---: | --- | ---: | ---: | ---: | ---: |
| 300/s | 实际速率 | 242/s | 299/s | 298/s | 299/s |
| 300/s | 成功 P95 | 2,727 ms | 196 ms | 461 ms | 135 ms |
| 500/s | 实际速率 | 258/s | 410/s | 473/s | 498/s |
| 500/s | 成功 P95 | 5,362 ms | 2,149 ms | 1,345 ms | 238 ms |
| 800/s | 实际速率 | — | 469/s | 466/s | 669/s |

- 稳定档位由 200/s 提升到 500/s，最高完成速率由约 258/s 提升到约 669/s；
- B 步的缓冲池调整在 MySQL 重启后冷缓存下测得，收益不明显，主要价值是防止表持续增长后的性能退化；
- 经宿主机端口压测在 1,000/s 时出现 `connection refused`，日志确认来自 Docker Desktop 的端口转发而非服务。因此最终结果（第 3 节）改为 k6 在 compose 网络内直连网关，同一套代码在 1,000/s 下 P95 37 ms、零错误。宿主机端口口径下 800/s 的排队有一部分来自这层转发，最终容量以第 3 节为准。

## 6. 剩余瓶颈与后续方向

- 同一活动只有一个写线程，这是单活动吞吐的上限；继续提升需要库存分桶（多个写分片各持一部分库存）；
- 压测器与服务同机，CPU 互相影响；正式容量规划应使用独立压测机和 30 分钟以上的稳态测试；
- 混沌测试中停机 17 秒内的请求直接失败，多实例部署和网关重试可以缩短不可用时间。

## 7. 可用于简历的表述

> 基于 k6 和 2 万个独立买家、默认限流配置，在本机 Docker 单实例环境下：持续 1,000 次/秒下单 2 万次全部成功，P95 37 ms、零错误；1 万名买家以 2,000 次/秒争抢 1,000 件库存，恰好成交 1,000 单、每人最多 1 单、零超卖；压测中强杀交易服务，重启后对账任务自动修复 2 件泄漏预占，全程无超卖。通过 JFR 与 `performance_schema` 定位到单用户压测掩盖的热路径数据库往返问题，同口径下 500 次/秒的 P95 从 5.4 s 降至 238 ms。

引用时请保留“本机 Docker 单实例”和压测口径等限定条件。
