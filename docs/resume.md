# 简历项目描述模板

## 项目名称

FlashFlow 高并发限量购与订单履约平台

## 技术栈

Java 21、Spring Boot 4.1、Spring Cloud Gateway、Spring Security、MySQL 8.4、Redis 8、Lua、Kafka 4.3、JPA、Flyway、Vue 3、TypeScript、Docker Compose、Prometheus、JUnit 5、Testcontainers、k6

## 项目描述

面向限量商品瞬时高并发场景设计的微服务电商系统，包含用户商城、运营后台、API 网关、交易服务和异步通知服务；商品域采用类目、SPU、SKU、秒杀活动四层模型，覆盖多字段检索、运营定价、上下架、库存划拨、鉴权限流、订单支付与取消、退款审批、已购评价、可靠消息、消费幂等、监控与容器化交付。

## 可直接使用的职责亮点

- 设计类目、SPU、SKU、秒杀活动四层商品模型，支持多颜色/规格独立库存、商品与 SKU 启停、活动库存划拨和个人限购，并通过角色权限隔离运营与购买链路；
- 实现覆盖商品名称、描述、类目、SKU 编码、颜色和规格的组合检索，支持价格/评分排序、可见评价聚合和管理员 SKU 独立定价，并校验原价与未结束活动价的约束；
- 设计 Redis Lua 原子预占方案，将库存校验与扣减、累计限购和请求幂等合并为单次原子执行，并以 MySQL 原子条件扣减作为最终防超卖屏障；
- 基于 `Idempotency-Key + 用户 ID`、数据库唯一索引和 Kafka Inbox 表构建 HTTP、订单、消费三层幂等，处理客户端重试与消息重复投递；
- 设计库存分桶写入：每个活动的 MySQL 库存拆为多行，由独立写分片并行提交，Redis 保留全局精确计数做准入；某桶不足时订单整组转投下一个桶，所有桶都拒绝才判定售罄，避免“局部售罄”导致少卖。同口径 A/B 压测中，单活动从单写线程约 2,100 单/秒（16%～36% 请求被拒）提升到 3,000 次/秒全部成交、P95 294 ms，零超卖；
- 使用 Transactional Outbox 将订单与领域事件纳入同一 MySQL 事务，通过 Kafka `acks=all`、幂等 Producer、指数退避和 DLT 实现至少一次可靠投递；并实现可切换的 Debezium CDC 模式（binlog 捕获、同事务插入后删除，消息格式与轮询模式一致），1,000 次/秒下事件端到端 P95 从 159 ms 降至 77 ms，2,000 次/秒下从 6.5 s 降至 1.8 s；
- 实现 `待支付→已支付→退款中→已退款` 订单状态机和独立售后申请模型，支持主动取消、15 分钟超时关单、退款审批及审计意见，并在事务提交后通过带订单号校验的 Lua 脚本补偿 Redis；
- 建立“已支付订单才能评价、每单一次”的已购评价约束，支持 1～5 星评分、前台平均分聚合、后台显隐审核和商家回复；
- 设计 Redis 库存自愈闭环：将取消、超时关单、退款后的缓存回补建模为与 MySQL 库存回补同事务落库的补偿任务，依托 Lua 按订单号幂等实现提交后即时执行、指数退避重试和后台人工重试；再以“行版本号与 Redis 值在静默窗口内不变”识别真实漂移，用 Lua CAS 修复并写审计日志，解决补偿失败后 Redis 永久偏少、活动提前售罄的问题；
- 基于 Testcontainers 搭建与生产同版本的 MySQL、Redis、Kafka 集成测试，验证 120 个买家并发抢 30 件恰好成交 30 单、同一幂等键并发 40 次只生成 1 笔订单、全部订单事件以订单号为 key 进入 Kafka，并通过 `docker pause` 注入 Redis 故障，验证补偿任务恢复后库存只回补一次；
- 在“零静默窗口激进对账 + 150 并发买家”的最坏情况测试中发现：Redis 偏大时合并批次总量超过剩余库存会整批失败，40 件仅售出 12 件；引入 `SOLD_OUT` 二分拆批重试后全部售出且无超卖；
- 搭建 Spring Cloud Gateway 统一入口，实现 JWT 双重校验、Redis 令牌桶限流和 Trace ID 透传，使用 Actuator/Prometheus 暴露 JVM、HTTP 与业务指标，并为连接池等待、写队列拒绝、Outbox 投递失败、补偿积压与库存漂移配置分级告警规则；
- 采用 Maven 多模块、Flyway 版本化建表、Docker Compose 一键环境，GitHub Actions 分别执行单元测试、Testcontainers 集成测试和前端构建，保证项目可复现交付。

## 性能实测

> 使用 k6 与 2 万个独立买家、默认限流配置，在 16 核 32 线程本机 Docker 单实例环境下：1,000 次/秒持续下单 2 万次全部成功，P95 37 ms、零错误；1 万名买家以 2,000 次/秒争抢 1,000 件库存，恰好成交 1,000 单、每人最多 1 单、零超卖；压测中强杀交易服务，重启后对账任务在 31 秒内自动修复泄漏预占，全程无超卖。多买家压测暴露了单用户压测因缓存命中而掩盖的热路径数据库往返，通过 JFR 与 `performance_schema` 定位并优化后，同口径 500 次/秒的 P95 从 5.4 s 降至 238 ms。

可直接替换上面第 4 条的职责描述：

- 用数万个独立买家做 k6 分档压测并逐层定位瓶颈：JFR 发现单用户压测因缓存命中掩盖了每单约 7 次 MySQL 往返（同口径 500 次/秒 P95 5.4 s → 238 ms）；`Innodb_row_lock_waits` 定位到 Outbox 清理语句在 REPEATABLE READ 下的间隙锁造成每分钟 7～14 秒的写入停顿；UUIDv7 事件 ID 测出发布器轮询需对整个积压排序、越落后越慢，改用复合索引后投递速度从 63 提升到 2,510 条/秒。

## 根据年限裁剪

应届/初级保留 3-4 条，重点讲清 Lua、防超卖、Outbox 和幂等；有经验岗位可增加库存自愈、故障注入测试、容量规划、监控告警和演进到 CDC/Kubernetes 的取舍。

推荐组合（每条都能在代码和测试里找到证据）：

| 岗位侧重 | 建议保留 |
| --- | --- |
| 高并发 / 交易 | Lua 原子预占、库存分桶、性能实测与瓶颈定位、二分拆批 |
| 分布式一致性 | Outbox + Inbox（轮询 / CDC）、三层幂等、库存自愈闭环 |

## 可展开的难点

**库存分桶的公平性。** 单写队列避免了热点行锁竞争，但单活动吞吐被一个写线程卡住（压测约 2,100 单/秒）。把库存拆成 4 行、各由独立写线程提交后，难点是“某个桶先卖完、别的桶还有库存”会把买家误判为售罄。做法是让 Redis 保留全局精确计数负责准入——被放行的订单总量不会超过总库存，因此一定能在某个桶成交——MySQL 侧放不下的订单整组转投下一个桶，沿用二分拆批和“已拒绝最小批量”剪枝，所有桶都拒绝才返回售罄；订单记录所用的桶，退款时回补原桶。单元测试覆盖了 3 个桶为空、库存全在一个桶的极端情况。

**补偿失败后的库存泄漏。** 取消订单时 MySQL 已回补，但 Redis 补偿只打日志，一次 Redis 抖动就会让活动永久少卖。做法是参照 Outbox 把补偿变成同事务落库的任务，靠 Lua 的订单号校验保证重试幂等；对账作为最后防线，用版本号和静默窗口区分在途预占与真实泄漏，用 CAS 避免与并发预占互相覆盖。结果：故障注入测试中 Redis 冻结期间取消的订单，在恢复后库存恰好回补一次。

**用测试找到的少卖问题。** 为验证对账“修错了也不会超卖”，写了零静默窗口的最坏情况测试，结果确实没超卖，但 40 件只卖出 12 件。日志显示 Redis 被修到偏大后，合并批次的总扣减量超过剩余库存，条件更新整批失败。改为批次 `SOLD_OUT` 时二分拆批重试，正常路径零开销，异常路径最多 O(log n) 次事务，测试改为断言 40 件全部售出。
